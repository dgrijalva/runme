# Runme Implementation Plan

## Context

Building a code-based task runner in Rust. Replaces config-file runners (make, npm scripts) with executable Rust files (RUNME.rs) that define tasks as code. Three target users: power developer (TUI), AI agent (CLI/MCP), non-technical colleague (guided TUI). See `docs/system_design.md` for full design.

Key architectural shift: `#!/usr/bin/env runme` instead of cargo-script's nightly shebang. The `runme` binary owns the entire compile-and-run pipeline.

## Crate Structure

```
runme/
├── Cargo.toml              (workspace root)
├── crates/
│   ├── runme-macros/       (proc-macro crate: #[task], #[init], derives)
│   │   ├── Cargo.toml
│   │   └── src/lib.rs
│   ├── runme/              (library: runtime, task system, TUI, log engine)
│   │   ├── Cargo.toml
│   │   └── src/
│   │       ├── lib.rs
│   │       ├── prelude.rs
│   │       ├── task.rs     (Task, TaskContext, Registry)
│   │       ├── process.rs  (child process management)
│   │       ├── log.rs      (structured log parsing, ring buffers)
│   │       ├── watch.rs    (file watching)
│   │       └── tui/        (ratatui UI)
│   └── runme-cli/          (binary: discovery, compilation, dispatch)
│       ├── Cargo.toml
│       └── src/
│           ├── main.rs
│           ├── discover.rs (find RUNME.rs files using `ignore` crate)
│           └── compile.rs  (compile, cache, and exec RUNME.rs files)
├── docs/
│   └── system_design.md
└── examples/
    └── RUNME.rs            (example runme file)
```

## Phases

### Phase 1: Workspace & Core Types ✓
**Goal:** Compilable workspace with the fundamental type system that everything builds on.

- Set up Cargo workspace with three crates
- Define core types in `runme` lib:
  - `TaskDef` — name, description, group, function pointer, metadata (watch patterns, deps)
  - `TaskContext` — handle passed to task functions. Provides exec, spawn, output capture.
  - `Registry` — collects tasks from inventory, provides lookup/listing
- `#[runme::task]` and `#[runme::init]` attribute macros in `runme-macros` using `syn` + `quote`
  - `#[task]` transforms an annotated fn into a registered task with metadata (including `group` field, `///` doc comments as description)
  - `#[init]` registers a per-file initialization hook via `inventory`
- `GroupDef`, `InitDef`, and `InitContext` types in the library
- Re-export macros from `runme` lib
- Minimal RUNME.rs example that compiles standalone

The entry point (`fn main()`) is generated by the build system's runner crate, not by a macro in the RUNME.rs file. See `docs/build_system_design.md` for the full compilation model.

**Key dependency:** `syn`, `quote`, `proc-macro2`, `inventory`

### Phase 2: Discovery & Compilation Pipeline ✓
**Goal:** `runme` CLI can find RUNME.rs files and compile/run them.

- RUNME.rs discovery in `runme-cli`:
  - Walk up from cwd to find nearest RUNME.rs (root)
  - Walk down to discover child RUNME.rs files
  - Uses `ignore` crate (respects .gitignore)
- Multi-file compilation pipeline (see `docs/build_system_design.md` for full spec):
  - Generate a Cargo workspace in a cache directory (`~/.cache/runme/<hash-of-root-path>/`)
  - Each RUNME.rs becomes a library crate; a generated runner crate depends on all of them
  - Source transformation: strip shebang, strip frontmatter, inject group constant, append `__runme_link()` for linker
  - Path dependency rewriting: resolve relative paths against original RUNME.rs location
  - Always regenerate workspace, always `cargo build` (Cargo handles incremental compilation)
- Dependency frontmatter: `//!` doc comment block parsed into generated Cargo.toml
- Shebang support: `#!/usr/bin/env runme` — discovers full tree, builds, runs
- Task groups: each RUNME.rs file's tasks are grouped by path, overridable via `#[runme::init]`
- Task disambiguation: root tasks win short names, `group:task` qualified syntax for child tasks
- `runme --list` — discover tasks and print them with group prefixes

**Not yet implemented:** `runme init` (project scaffolding)

**Key dependencies:** `ignore`, `sha2`

### Phase 2b: TUI Foundation ✓
**Goal:** Basic TUI shell with task execution wired through, proving the full pipeline.

- `tracing::Layer` converting task function events to `LogEntry`s in an `OutputBuffer`
- `tracing` macros (`info!`, `error!`, etc.) re-exported from prelude
- `ctx.stop_all()` for terminating all spawned processes
- ratatui app shell with async event loop (60fps dirty-flag rendering)
- Terminal setup/teardown with panic hook for safe restoration
- Signal handling (SIGINT/SIGTERM) for clean shutdown
- `TaskRunner` orchestrator: launches tasks, tracks status transitions, monitors spawn events
- `TaskContext` spawn notification channel for TUI process discovery
- `LogStore` integration: tracing output, exec output, and spawn output all flow to the viewer
- Generated runner binary wires `runme` (no args) and `runme <task>` to the TUI

**Key dependencies:** `ratatui`, `crossterm`, `tracing`, `tracing-subscriber`

### Phase 3: Process Management ✓
**Goal:** Reliable primitives for running, capturing, and controlling child processes.

- `TaskContext::exec()` — run a command, capture stdout/stderr into ring buffer, stream to log engine
- Process group management — spawn children in process groups for clean shutdown (`setpgid`, `killpg` via nix)
- Signal handling:
  - Forward signals (SIGINT, SIGTERM, SIGHUP) to child processes
  - SIGHUP for reload semantics (user or agent can trigger re-run without full restart)
  - Clean shutdown: `stop_all()` sends SIGTERM with grace period, escalates to SIGKILL
- Output capture:
  - Per-task ring buffer (bounded, configurable size) in `OutputBuffer`
  - Structured log detection: if a line parses as JSON, store it structured
  - Raw fallback for non-JSON output
- Parallel execution: run multiple tasks concurrently via `Registry::run_parallel` / `JoinSet`
- Health checks: `ProcessHandle::is_running()`, `ctx.watch_channel()` for custom status

**Not yet implemented:** Declarative readiness conditions (HTTP endpoint, log line match, port open)

**Key dependencies:** `tokio` (runtime, process, sync, signal), `nix` (process groups, signals)

### Phase 3b: Command API ✓
**Goal:** Structured command builder that separates "what to run" from "how to run it." See `docs/system_design.md` § Command API.

- `Cmd` type in `crates/runme/src/cmd.rs` — program, args, env overlays, working directory
- `Cmd::new("program").args([...]).env("K", "V").cwd("./path")` builder API
- `Cmd::shell("string")` — wraps in `sh -c` for pipes/globs/redirects
- `&str` → `Cmd::shell()` implicit conversion so `ctx.exec("echo hi")` still works
- `From<std::process::Command>` via `get_program()`, `get_args()`, `get_envs()`
- `ctx.exec()` and `ctx.spawn()` accept `impl Into<Cmd>`
- Cmd is a pure value — no timeout, retry, or runtime behavior (those live on the execution side)
- Working directory relative to RUNME.rs file location
- Environment inherits from parent process, overlays additions
- Optional `label`, `RecordParser`, and `FieldExtractor` overrides per command

### Phase 4: Task Arguments & Invocation ✓
**Goal:** Unified argument model that serves CLI, cross-file invocation, and agents through the same mechanism. TUI updated to support the resulting task tree.

**Task arguments** — progressive complexity (see `docs/system_design.md` § Task Arguments):
  - Simple: extra function params → auto-generated `--name <value>` flags from name/type
  - Full control: single `clap::Parser` struct param → full clap derive features
  - The `#[task]` macro detects which form from the function signature and generates the parsing wrapper
  - Argument metadata extractable from the parser via `ArgMetadataFn` on `TaskDef`

**Cross-file invocation:**
  - `ctx.run("name", &["--flag", "val"])` — invoke any task through the registry with string args
  - `ctx.tasks()` — query the registry; returns `Option<TaskQuery>` with `.all()` and `.matching("glob")` methods
  - Same parsing wrapper handles CLI args and programmatic string args
  - Leaf-to-root load ordering guarantees child tasks are registered before root tasks run
  - Registry shared via `Arc<Registry>`, injected into TaskContext in both TUI and CLI modes

**Task observation:**
  - `#[task]` macro injects `let _task = ctx.start_task("name")` — RAII `TaskGuard` notifies runtime on enter/exit via tracing events
  - Direct calls into `TaskContext`, not tracing spans

**Steps (observability):**
  - `ctx.begin_step("name")` — RAII `StepGuard`, active until dropped
  - `.fail("reason")` for explicit failure annotation
  - Emits `step_start`/`step_end` tracing events with success/failure status
  - Purely presentational: TUI and agents see step transitions, no control flow implications

**TUI: multi-task support:**
  - `TaskSession` tracks per-task status, processes, and output
  - `TaskRunner` supports multiple concurrent sessions via repeated `launch()` calls
  - Sidebar renders task tree with depth-based indentation (tasks at depth 0, processes at depth 1)
  - Monitor loop routes `SpawnEvent`s to the correct session by task name

**Raw output:** `ctx.println()` emits undecorated text through the output buffer — works in TUI (appears in log viewer), CLI (forwarded to stdout), and cross-invocation (flows through log engine).

**Not yet implemented:** `ctx.run().spawn()` for backgrounding tasks with a handle.

**Key dependencies:** `clap`

### Phase 4b: CLI Polish ✓
**Goal:** Fully functional CLI for humans and agents.

**Argument parsing:**
- `RunmeArgs` clap Parser in the runme library — optional `--ui` mode, plus `rest: Vec<String>` for task name + task args
- Two-stage parsing: runme args first, then task name resolution, then task-specific parser on remaining args
- Generated runner main is minimal (~75 lines): linking, init, then `runme::cli::run(registry, group_names)`
- UI mode resolution: explicit `--ui` flag > task's `UiHint` > terminal detection (auto-fallback to CLI when no TTY)

**Built-in commands as tasks:**
- `list` is a `#[runme::task]` function in the runme library, registered in the `builtin` group
- Uses `extern crate self as runme;` in lib.rs so the macro's `::runme::` paths resolve inside the crate
- `:` prefix aliases to `builtin:` — `runme :list` == `runme builtin:list`
- Standard disambiguation applies: `runme list` works unless masked by a user task
- `UiHint::Cli` on built-in tasks defaults them to CLI mode (no TUI flash for utility commands)

**UI modes** (`--ui tui|cli|agent`):
- TUI (default when terminal available): interactive log viewer, task picker
- CLI: tracing subscriber on stderr, process output forwarded to stdout/stderr in real time
- Agent: structured JSON output, minimal tokens

**Not yet implemented:**
- Shell completion generation (bash/zsh/fish) via `clap_complete`
- `--timeout <duration>` (parsed but not enforced)
- `--filter` for log filtering on stdout (parsed but not wired)
- `runme :logs <task>` — tap into running task's log buffer
- `completions` built-in task
- Macro attribute for `default_ui` (currently only settable via manual `TaskDef` construction)

**Key dependencies:** `clap`

### Phase 5: Log Engine & Structured Output ✓
**Goal:** First-class log viewing, filtering, and export.

- Structured log parsers in `crates/runme/src/log/parse/`: JSON, logfmt, cargo diagnostics, rust panics, plain text — chained via `FallbackParser` with sticky active parser
- `FieldExtractor` trait: extracts timestamp, level, message, additional fields from parsed records
- Filter engine: full expression AST with AND/OR/NOT, field paths (dotted notation), matchers (exact, substring, regex, numeric comparisons, wildcard)
- Multi-source composition: `LogStore` aggregates entries from multiple sources with broadcast subscribers
- Search: full-text with regex mode, case sensitivity, context lines, match range tracking
- `OutputBuffer` ring buffer with `tokio::broadcast` for subscriber notifications

**Not yet implemented:**
- Named FIFOs per task for external consumption
- `runme logs <task> --follow` for live tailing from CLI
- Export/dump captured logs to file from CLI

### Phase 6: TUI — Exploration Phase ✓
**Goal:** Prototype the TUI interaction model. This phase is exploratory.

- Async ratatui app shell with 60fps dirty-flag rendering
- Fuzzy picker (`SkimMatcherV2`) for task selection, grouped by source, browse + search modes
- Sidebar: task/process list with running/stopped status, signal controls (s=SIGTERM, S=SIGHUP), toggle with `\`
- Log viewer: scrollable, searchable, per-source color coding, wrap/truncate toggle
- Vim-style navigation: j/k, Ctrl-d/u, g/G, page up/down
- Filter mode (`f`) and search mode (`/`) with n/N for next/prev match
- Detail overlays: entry detail (expanded log entry), process detail (with lsof socket inspection)
- Source visibility toggles: 1-9 quick toggles, `a` for all, Space/Enter per-source
- Runtime task controls: signal processes from sidebar
- Export visible log to file (`e`)
- App modes: TaskPicker, Normal, FilterInput, SearchInput, Help, EntryDetail, ProcessDetail

**Key dependencies:** `ratatui`, `crossterm`, `fuzzy-matcher`

**Resolved questions:**
- Layout: sidebar task list + main log view, sidebar toggleable
- Filtering: modal — `f` enters filter input mode, `/` enters search mode
- Watch rebuilds: surface via log entries and process status changes in sidebar

**Not yet implemented:**
- Command palette
- History: recent/frequent commands surfacing
- Pause watch from TUI

### Phase 7: Introspectable Composability — Resolved
**Goal:** Find the right boundary between "it's just code" and "the runtime can see the structure."

**Decision:** Observe, don't declare. The runtime watches task execution as it happens — no forward-declared step graph. The observation hierarchy:

1. **Tasks** — `#[task]` macro provides enter/exit visibility (already implemented)
2. **Steps** — RAII `ctx.begin_step("name")` for presentational labeling (Phase 4)
3. **Commands/watches** — `ctx.exec()`, `ctx.spawn()`, `ctx.watch()` already tracked by runtime

Cross-file invocation (`ctx.run()`) and task discovery (`ctx.tasks()`) provide the composability layer. Same-file tasks are direct function calls with typed args. Cross-file tasks go through the registry with string args — same mechanism as CLI and agents.

See `docs/system_design.md` § Task Lifecycle & Runtime Visibility for full design.

### Phase 8: AI Agent Integration
**Goal:** MCP server and agent-optimized workflows.

- MCP server exposing tasks as tools:
  - `runme_list` — discover available tasks
  - `runme_start` — start a task, return a handle
  - `runme_status` — check task state
  - `runme_logs` — query logs with filters
  - `runme_stop` / `runme_signal` — control running tasks
- Prompt/skill documents: teach agents how to create, interpret, and execute RUNME.rs files
- Token optimization: filtering, summarization, structured output that minimizes tokens while preserving signal

## Remaining Work

Phases 1–6 and 7 (design) are complete. Phase 4 and 4b are implemented. What remains:

1. **Phase 4b polish** — shell completions (`clap_complete`), `--timeout` enforcement, `--filter` wiring, `completions` built-in task, macro `default_ui` attribute.
2. **Phase 8** (AI/MCP integration) — expose the invocation model via MCP. The unified argument interface (`ctx.run()`, string args, `Registry::resolve()`) makes this mostly plumbing.
