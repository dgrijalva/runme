# Invoking Tasks

The current API for executing a sub-task from inside a task is poor: `ctx.run("build_wasm", &["--watch"])` takes a string name and a slice of string arguments, even though both caller and callee live in the same process. Direct function calls (`build_wasm(ctx, true, false).await?`) sidestep the strings but bypass the framework entirely — the called task is not registered as a child, its logs are not routed to a distinct source, it shares the caller's cancellation/ready state, etc. This document describes a redesign that makes the typed path the default while keeping the dynamic path for cases where it earns its keep.

## Status quo

Two existing paths, with complementary defects:

**String-keyed framework path.**
```rust
let wasm = ctx.run("build_wasm", &["--watch"]).spawn()?;
wasm.wait_ready().await?;
```
- Full framework integration: child task registration, log routing, ready state, cancellation, timeout watchdog, summary capture.
- Untyped: task name is a string, args are stringified then re-parsed by the callee's clap parser. Renaming a task breaks call sites silently at runtime. IDE has no idea what's going on. Non-string argument values round-trip through their `Display`/`FromStr` impls.

**Direct function call.**
```rust
build_wasm(ctx, true, false).await?;
```
- Fully typed at the call site. Renames are compile errors. Arguments retain their Rust types.
- No framework integration. The callee's body runs as if inlined into the caller's task — same TaskId, same log source, same cancellation token, no separate ready signal, no per-invocation timeout. The two tasks are smeared together.

The goal of this redesign is a single call shape that is both fully typed and fully framework-integrated, with the dynamic path preserved for the cases where it is actually the right tool.

## Design

### 1. The macro rewrites user fns into builder-returning shims

`#[rnme::task]` already does most of the work needed; it currently registers a `TaskDef` whose function pointer invokes the user-written body. The redesign:

- The user-written body moves into a private symbol the framework calls.
- The user-facing symbol with the original name becomes a thin shim with the *same parameter list* but a return type of `TaskBuilder<()>` (or similar) instead of the `impl Future<Output = TaskResult>` the body returned.
- The shim packages the typed args, looks up the (statically known) `TaskDef`, and returns a builder.
- `.await` (via `IntoFuture`) and `.spawn()` on that builder go through the existing engine path — `EngineInternals::spawn_child` and friends — to register the child task, set up the TaskId, route logs, install the cancellation token and any timeout, and (for `.spawn()`) hand back a `TaskHandle`.

Net effect at the call site:

```rust
let wasm = build_wasm(ctx, false, true).spawn()?;       // drops the "--watch" string
wasm.wait_ready().await?;
build_wasm(ctx, true, false).await?;                     // now a real child task
```

Both lines have the same syntactic shape as a normal Rust fn call; the difference is that they don't actually run the body — they return a builder that the framework drives.

**`#[must_use]` on the builder.** Because the shim returns a `TaskBuilder` rather than running directly, a call like `build_wasm(ctx, true, false);` without `.await?` or `.spawn()?` is a silent no-op — the builder is constructed and dropped. The builder type is annotated `#[must_use]` so this pattern produces a compiler warning in all three forms (no-args, simple-args, struct-arg). `SpawnBuilder` should carry the same annotation for consistency if it doesn't already.

**Argument forms at the call site.** The existing three forms (no-args; simple primitives; single struct arg) are preserved. Positional calling stays the rule:

- 0-arg tasks: `build(ctx).await?`
- Simple-primitive tasks: `build_wasm(ctx, true, false).await?`
- Struct-arg tasks: `web(ctx, WebOpts { ... }).await?`

If positional calling becomes unreadable because a task accumulates many primitive params, the author is expected to refactor the task into a struct arg (Form 3). No special call-site machinery (named-arg builders, sibling args structs, etc.) is generated by default — see *Possible future enhancements* below.

### 2. The dynamic path is retained

`ctx.run(name, args)` still exists. The string-keyed path remains the right tool for:

- Discovery-driven fan-out: `for task in ctx.tasks().matching("*:clean") { ctx.run(&task.qualified_name, &[]).await?; }`.
- MCP-driven invocation (the agent passes a string).
- CLI re-entry / scripted glue.
- Cross-file invocation that isn't statically known.

Both paths converge on the same `TaskDef` and the same engine-side machinery. They are not two implementations — they are two front-ends to one runtime.

### 3. Cross-file calls: the `subtasks` module tree

The workspace generator already knows the full set of RUNME.rs files and their directory layout. The redesign uses that to auto-inject a module hierarchy into each RUNME.rs's generated crate, mirroring the directory tree of its discovered descendants. The hierarchy lives under a single, non-public `mod subtasks` at the crate root so that nothing about the cross-file machinery leaks into the parent's own namespace or transits through child crates.

Given:
```
monorepo/RUNME.rs
monorepo/search_agent/RUNME.rs
monorepo/prompts_service/RUNME.rs
monorepo/prompts_service/director_client/RUNME.rs
monorepo/service_common/api_client/RUNME.rs   (service_common/ has no RUNME.rs)
```

The codegen, when generating the crate for `monorepo/RUNME.rs`, injects something like:

```rust
mod subtasks {                                          // not pub — local to this crate
    pub mod search_agent {
        pub use ::search_agent_crate::*;
    }
    pub mod prompts_service {
        pub use ::prompts_service_crate::*;
        pub mod director_client {
            pub use ::director_client_crate::*;
        }
    }
    pub mod service_common {                            // structural — no RUNME.rs at this level
        pub mod api_client {
            pub use ::api_client_crate::*;
        }
    }
}
```

Call sites from the root:

```rust
subtasks::search_agent::web(ctx, opts).await?;
subtasks::prompts_service::deploy(ctx).await?;
subtasks::prompts_service::director_client::build(ctx, true).await?;
subtasks::service_common::api_client::regen(ctx).await?;

// constructing typed args works the same way — the child's pub types travel with it
let opts = subtasks::search_agent::WebOpts { /* ... */ };
subtasks::search_agent::web(ctx, opts).await?;
```

Properties:

- **`mod subtasks` is non-`pub`.** It exists for the calling crate's source to write against; it is not part of the crate's public surface. The child's own `mod subtasks` (also non-`pub`) is therefore never visible from the parent, which is what keeps `subtasks::project::subtasks::child` from happening. Each crate has its own local view of its own descendants and nothing more.

- **Each parent crate materializes its full descendant subtree directly.** Codegen walks the discovered descendants and emits the nested module structure itself, reaching descendant crates by name (`::api_client_crate::*`) rather than chaining through children's exports. The cargo dep graph reflects this — each crate declares deps on every RUNME crate in its discovered subtree. Authors never write any of this.

- **`pub use ::child_crate::*` re-exports the child's full public surface**, not just task shims. Task fns (emitted as `pub fn` by `#[rnme::task]`) come along; so do any `pub struct` / `pub enum` / `pub fn` / `pub use` items the child author wrote. This is necessary because Form-3 tasks require their argument types at the call site, and authors may want to share helper types or constants across files. The cost is that things the child author marked `pub` *do* propagate up — usually fine; occasionally an author will need to be deliberate about what they mark `pub` in a RUNME.rs.

- **Paths mirror directory structure**, not the structure of RUNME.rs files. Intermediate dirs without a RUNME.rs appear as empty structural modules iff they are on the path to a descendant that has one. Dirs without any RUNME.rs descendants do not appear at all. `src/`, `tests/`, `bin/`, etc. never appear because they contain no RUNME.rs.

- **Adding a middle-tier RUNME.rs is non-breaking.** If someone later adds `monorepo/service_common/RUNME.rs`, the path `subtasks::service_common::api_client::regen` continues to resolve; the only change is that `subtasks::service_common::` now also has the new file's pub items attached at the module root via `pub use ::service_common_crate::*`. Existing call sites do not need to be updated. The same is true in reverse — removing a middle-tier RUNME.rs leaves descendant paths intact.

- **Sibling collisions are impossible by construction**, because two RUNME.rs files in different parent dirs end up at different module paths (`subtasks::services::api` vs `subtasks::tools::api`).

- **Inside a RUNME.rs, that file's own tasks are just local fns** — no path prefix needed. `prompts_service/RUNME.rs` calls its own `deploy` task as `deploy(ctx).await?`. The `subtasks::...::deploy` path is only relevant to callers from outside that file.

### 4. Sibling-to-sibling typed calls are not supported

If `services/api/RUNME.rs` wants to call a task in `services/worker/RUNME.rs`, the typed path will not work — neither file is in the other's discovered descendant set. Two ways out:

- The dynamic path: `ctx.run("services/worker:build", &[])`.
- Refactor the shared logic into a regular Rust lib crate that both sides depend on.

This is intentional. Every concrete sibling-to-sibling case we considered was better expressed as (a) a parent task orchestrating both children, or (b) a shared lib. "Calls flow downward in the tree" is a discipline that matches how monorepos are already organized.

### 5. Discovery boundary unchanged

`rnme` continues to walk up from cwd to find the nearest RUNME.rs as the root, then walks down to find descendants. The materialized module tree is rooted at the discovered root. Invoking from a leaf shows only that leaf's view; invoking from a parent shows the whole subtree. No global scope, no walking up past the discovered root, no change to the meaning of `rnme foo` from any directory.

### 6. Working directory follows the task, not the caller

Each task runs with its cwd defaulting to the directory of the RUNME.rs that defines it. This is essential for cross-file invocation: when a parent RUNME.rs calls into `subtasks::child::foo`, `foo` still runs as if invoked from `child/`. Relative paths in the child task's body (`./scripts/x`, `Cargo.toml`, `client_web/`) keep working without the child author having to think about whether they're being called from a parent.

Codegen records the originating directory in `TaskDef::dir` (a `const __RNME_DIR` injected next to `__RNME_GROUP`). At task launch, the engine writes it onto the `TaskContext`. `ctx.spawn(cmd)` resolves the subprocess cwd before launch: no `.cwd()` defaults to `task_dir`, a relative `.cwd(p)` becomes `task_dir.join(p)`, and an absolute `.cwd(p)` is left alone. The `rnme` process never `chdir`s, so concurrent tasks from different RUNME.rs files don't fight over a shared cwd. `ctx.task_dir() -> Option<&Path>` exposes the path for body-side Rust code that needs to join from it.

### 7. Collision strategy

Collisions split into two classes that demand different treatment:

- **Class 1 — collisions inside RUNME.rs files.** Caused by choices the RUNME author makes (task names, items they mark `pub`, etc.). Surface as cargo errors at build time, pointing at the offending line. The author owns these files and can rename. No design accommodation needed.

- **Class 2 — collisions imposed by the project's file layout.** Caused by directory names the project owns for reasons unrelated to rnme (services named after crates, mixed dash/underscore conventions, etc.). The RUNME author cannot resolve these by editing RUNME files alone unless we provide a way. rnme **must not become a design constraint on the project it's helping with**, so for Class 2 we either design the collision out or provide an escape hatch that lives entirely inside RUNME files.

The `subtasks` wrapper from §3 designs away most of Class 2 structurally: child dir names cannot collide with the parent's external imports or with `rnme::prelude` items, because they live behind `subtasks::` rather than at the parent's crate root. The wrapper name itself (`subtasks`) is a Class 1 surface — it would collide with a user task named `subtasks`, fixed by renaming the task — and chosen to be implausible as a task name.

**The one Class 2 case that remains: normalization-sibling collisions.** Two siblings whose directory names normalize to the same Rust identifier — e.g. `foo-bar/` next to `foo_bar/`, or `Foo/` next to `foo/` — would both want the same module name inside `subtasks::parent::`. The `subtasks` wrapper does not solve this because both names already live inside the wrapper.

For this case, rnme provides a frontmatter override: `[rnme.rename]`.

```rust
// at the top of the child RUNME.rs whose normalized name needs to differ:
//! [rnme.rename]
//! name = "foo_bar_dashed"
```

Semantics:
- The replacement string is substituted for the directory name **before normalization**. The same normalization pass then runs on the new name. So `name = "foo_bar_dashed"` produces the identifier `foo_bar_dashed`; `name = "Hello World"` would produce `hello_world`.
- Renaming is available to any RUNME.rs for any purpose, not only collision resolution. An author can use it for clarity, branding, or to decouple the exposed name from the on-disk name.
- When a sibling normalization collision is detected at codegen and not resolved by a rename, the build fails with an error that names both colliding paths and shows the exact frontmatter snippet the author should add to one of them.

Direction-1's structural protection plus this single escape hatch covers Class 2 entirely without making rnme a constraint on the project's layout.

## Possible future enhancements

Captured here so they aren't lost; not part of the initial design.

- **Per-task fluent builder for Form-2 tasks.** The macro could optionally emit a fluent builder for tasks with simple primitive params, so the call site reads as `build_wasm(ctx).watch(true).spawn()` instead of `build_wasm(ctx, false, true).spawn()`. This would give Form-2 tasks named-arg ergonomics with default-friendly partial calls, at the cost of a larger macro footprint per task and a divergence in call shape between Form-2 and Form-3. Worth revisiting if positional Form-2 calls turn out to be a recurring pain in practice.

## Non-goals

- **Direct-inline escape hatch.** No mechanism is provided to call a task's body directly without going through the framework. If an author wants reusable logic that isn't a task, they should write a plain Rust fn. A task is a framework-integrated invocation by definition.
